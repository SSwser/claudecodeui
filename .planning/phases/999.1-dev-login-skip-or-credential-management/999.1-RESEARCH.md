**Date:** 2026-04-11

## Executive Summary

This phase adds `DEV_AUTO_LOGIN` — a development-only bypass for the auth flow modeled after the existing `IS_PLATFORM` pattern. The codebase already has all primitives needed; this is pure wiring with a minor new utility function. Two plans: server-side middleware, then frontend context + UI.

---

## Existing Auth Architecture

### IS_PLATFORM Pattern (Direct Template)

The existing `IS_PLATFORM` bypass is the canonical implementation template:

**Server** (`server/constants/config.js`):

```js
export const IS_PLATFORM = process.env.VITE_IS_PLATFORM === 'true';
```

**Server middleware** (`server/middleware/auth.js`):

- `authenticateToken`: checks `IS_PLATFORM` first → calls `userDb.getFirstUser()` → sets `req.user` → `next()`
- `authenticateWebSocket`: checks `IS_PLATFORM` first → calls `userDb.getFirstUser()` → returns user object

**Frontend** (`src/constants/config.ts`):

```ts
export const IS_PLATFORM = import.meta.env.VITE_IS_PLATFORM === 'true';
```

**Frontend** (`src/components/auth/context/AuthContext.tsx` — `useEffect`):

```ts
if (IS_PLATFORM) {
  setUser({ username: 'platform-user' });
  setNeedsSetup(false);
  void checkOnboardingStatus().finally(() => setIsLoading(false));
  return;
}
```

**Frontend** (`src/components/auth/view/ProtectedRoute.tsx`):

```tsx
if (IS_PLATFORM) {
  if (!hasCompletedOnboarding) return <Onboarding ... />;
  return <>{children}</>;
}
```

### Key Insight

The IS_PLATFORM bypass is **server-side stateless**: no JWT token is issued or required. Server simply injects `getFirstUser()` into `req.user` on every request. Frontend renders the app without a token. This is safe for development/platform scenarios.

`DEV_AUTO_LOGIN` follows the same model. Token persistence is not needed because every request bypasses validation on the server. D-10's requirement for "valid session" is satisfied by server-side injection — not by an actual JWT.

## Implementation Plan

### D-05: `shouldSkipAuth()` Utility (server)

```js
// server/constants/config.js addition:
export const IS_DEV_AUTO_LOGIN = process.env.VITE_DEV_AUTO_LOGIN === 'true';

// server/middleware/auth.js
import { IS_PLATFORM, IS_DEV_AUTO_LOGIN } from '../constants/config.js';

const shouldSkipAuth = () => IS_PLATFORM || IS_DEV_AUTO_LOGIN;

// Then use shouldSkipAuth() in both authenticateToken and authenticateWebSocket
```

### D-07: Auto-create dev user

In `authenticateToken` and `authenticateWebSocket`, if `shouldSkipAuth()` is true but `getFirstUser()` returns null (empty DB), fall back to creating a `dev` user:

```js
import bcrypt from 'bcrypt';

const ensureDevUser = async () => {
  let user = userDb.getFirstUser();
  if (!user) {
    const hash = await bcrypt.hash('dev', 10);
    user = userDb.createUser('dev', hash);
  }
  return user;
};
```

`authenticateToken` is async already. `authenticateWebSocket` is sync — needs to become async OR use a pre-computed user. The simplest safe approach: make `authenticateWebSocket` also async (check all callers).

### Frontend `VITE_DEV_AUTO_LOGIN` Flag

```ts
// src/constants/config.ts
export const IS_DEV_AUTO_LOGIN = import.meta.env.VITE_DEV_AUTO_LOGIN === 'true';
```

**Vite env handling**: `VITE_*` vars are automatically available via `import.meta.env`. Production builds tree-shake `false` branches when the env var is absent (dead code elimination). No need for additional `define` block in `vite.config.js` — existing `loadEnv` pattern handles this.

### D-03: Production Safety

Two independent guards:

1. Server: `IS_DEV_AUTO_LOGIN = process.env.VITE_DEV_AUTO_LOGIN === 'true'` — requires explicit env var, never true in production where var is not set
2. Frontend: `import.meta.env.VITE_DEV_AUTO_LOGIN === 'true'` — Vite treats missing vars as `undefined`, so condition is false. Production bundles tree-shake the branch away.

### D-06: Dev Mode UI Indicator

Project has no global toast library (confirmed: no sonner/react-hot-toast in package.json). The FileTree uses local `useState` toast with auto-timeout. For a persistent dev badge, a fixed-position banner is cleaner.

Recommended: small fixed banner in `ProtectedRoute.tsx` or `AuthProvider` — renders only when `IS_DEV_AUTO_LOGIN` is true, behind a Vite feature flag. Tailwind styling consistent with existing patterns.

```tsx
// Example fixed banner
{
  IS_DEV_AUTO_LOGIN && (
    <div className="fixed bottom-2 right-2 z-50 rounded bg-yellow-500/90 px-2 py-1 text-xs font-mono text-black">
      DEV AUTO-LOGIN
    </div>
  );
}
```

### D-08: Playwright Integration

`playwright.config.ts` webServer command is `npm run client -- --host 127.0.0.1 --port 4173`. To enable `DEV_AUTO_LOGIN` for E2E tests, tests need both frontend and backend running with `VITE_DEV_AUTO_LOGIN=true`. The env var on the Vite/webServer side handles the frontend. The server (not managed by Playwright config) needs `VITE_DEV_AUTO_LOGIN=true` in its process environment.

Simplest approach: document in `.env.example` and note that CI/E2E test scripts should set this var.

## Common Pitfalls

1. **`authenticateWebSocket` is sync** — needs to become async to `await bcrypt.hash()` for dev user creation. Must check all call sites in `server/index.js` or wherever WS upgrade happens.
2. **Don't use `IS_PLATFORM` string in synthetic dev user** — set `username: 'dev'` not `'platform-user'` to distinguish the two modes.
3. **`onboarding` flow applies to dev user too** — if the auto-created dev user hasn't completed onboarding, `ProtectedRoute` will show the Onboarding form. Either `completeOnboarding(userId)` when creating the dev user, or skip onboarding check in dev mode (simpler).
4. **Import bcrypt in auth.js** — it's already a project dependency but NOT currently imported in `auth.js` (only in `routes/auth.js`). Need to add the import.

## Validation Architecture

No external service dependencies. Manual verification:

1. Set `VITE_DEV_AUTO_LOGIN=true` in `.env`, restart dev server → app opens directly without login form
2. Open network tab → API calls succeed with 200 (no 401)
3. WebSocket connections establish correctly
4. Unset the var → login form appears as normal
5. Production build (`npm run build`) → `IS_DEV_AUTO_LOGIN` branch absent from bundle (verify via `grep -r DEV_AUTO_LOGIN dist/`)
