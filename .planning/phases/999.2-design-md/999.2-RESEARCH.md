## User Constraints (from CONTEXT.md)

### Locked Decisions

### 色彩对齐策略

- **D-01:** 直接替换 `.dark {}` 中的 CSS 变量值为 DESIGN.md 色板（`#07080a` background、`#101111` card surface、`hsl(195, 5%, 15%)` border 等），全局即时生效，不引入过渡层。
- **D-02:** 同步调整 light mode——基于 DESIGN.md dark 色板做明暗对称映射，一步到位更新 `:root` 变量值。
- **D-03:** 引入独立 `--brand` / `--brand-foreground` CSS 变量用于 Raycast Red (`#FF6363`)，与 `--destructive` token 分离。品牌色用于 CTA 和品牌标识场景，destructive 保留用于错误/危险状态。

### 排版系统迁移

- **D-04:** 本地托管 Inter + GeistMono 字体（woff2 格式放入 `public/fonts/`），通过 `@font-face` 声明加载。零网络依赖，FOUT 可控。
- **D-05:** 全局 `--font-weight-normal` 从 400 改为 500（medium），提升 dark mode 可读性。
- **D-06:** letter-spacing 通过 Tailwind 自定义 `tracking-*` class 按组件应用（body +0.2px、button/nav +0.3px），不全局设置。

### 阴影与深度层级

- **D-07:** 引入精简版 3 级阴影系统（subtle、ring、button），Key 和 Floating 后续按需添加。不一次引入全部 6 级。
- **D-08:** 阴影通过 cva 变体系统管理（`elevation: 'subtle' | 'ring' | 'button'`），与现有组件变体模式一致。
- **D-09:** 卡片边框采用 DESIGN.md 的 rgba 白边框 + 双环模式（`rgba(255,255,255,0.06)` border + `0px 0px 0px 1px` outer ring + inset ring）。

### 迁移范围与节奏

- **D-10:** Token 先行，组件跟进——第一步替换 CSS 变量（色彩、字体、字重、圆角），第二步更新组件层（阴影、边框、letter-spacing、hover 模式）。
- **D-11:** 复用 Phase 4 已有的 Playwright 视觉回归基线，更新截图对比验证视觉变更。
- **D-12:** 引入 DESIGN.md 圆角比例尺，扩展 `--radius` 为多级别 token（micro 2-3px、small 4-6px、medium 8px、large 12-16px、pill 86px+）。

### 交互模式

- **D-13:** 全局采用 opacity hover 模式（hover: opacity 0.6 过渡），替代当前 background 变化的 hover 模式。所有按钮、卡片、链接统一。

### 间距系统

- **D-14:** 切换为 px 基础 spacing token（`--spacing-1: 4px`、`--spacing-2: 8px`...），与 DESIGN.md 8px base unit 完全一致，替代现有 rem 基础值。

### 按钮变体

- **D-15:** 重新映射现有 Button 变体到 DESIGN.md 风格——default→Primary Pill（透明底 + 白字 + 86px圆角 + inset shadow）、secondary→Secondary（透明底 + 白字 + 6px圆角 + rgba border）、ghost→Ghost（无底无边 + 灰字→白字）、CTA→半透明白底深色字。更新样式但保持 variant API 兼容。

### OpenType Features

- **D-16:** OpenType features（calt、kern、liga、ss03）通过 Tailwind 自定义 class 按组件应用，不在 body 全局设置。

### 总体方针

- **D-17:** 不做向后兼容补丁处理。直接基于决策选择最优解实现，不保留旧样式的过渡层或兼容 shim。

## Summary

这不是“改一组 token 就结束”的阶段，而是“token 层 + primitive 层 + 高流量页面 + 长尾硬编码样式”四层联动的视觉迁移。现有仓库已经具备正确的总体骨架：`src/index.css` 持有 light/dark 语义变量，`tailwind.config.js` 用 `hsl(var(--token))` 做语义桥接，`src/shared/view/ui/Button.tsx` 与 `src/components/ui/button.tsx` 已把按钮 API 收敛到单点入口；这意味着 Phase 999.2 应该复用 Phase 4 的架构，而不是再引入第二套设计 token 系统。 [VERIFIED: codebase read]

真正的风险在于“长尾绕过层”很厚：至少 `128` 个源码文件含蓝/灰/红/绿等硬编码色阶，`100` 个文件含显式 `hover:bg-*` / `hover:text-*` / `hover:border-*` 覆写，`10` 个文件直接自带原生 `<button className=...>` 样式。仅替换 token 会让共享组件变好看，但不会自动收拢这些 feature 层的旧样式；因此规划上必须先做 token 和 primitive，再批量收壳层和高流量页面，最后才清理 feature 长尾。 [VERIFIED: terminal] [VERIFIED: codebase grep]

现有视觉回归基础可复用，但覆盖远不足以给这类全局样式迁移兜底。`tests/visual/baseline.spec.ts` 已使用 `toHaveScreenshot()`，可直接延续；但当前实际落库的快照只有 `auth-login-light.png` 与 `root-dark.png` 两张，且测试里存在 `waitForTimeout()` 和基于当前状态的 `test.skip()`。规划时应把“建立可重复的视觉夹具页面/状态”视为独立任务，而不是实施后临时补救。 [VERIFIED: codebase read] [VERIFIED: terminal] [CITED: https://playwright.dev/docs/test-snapshots] [CITED: https://playwright.dev/docs/test-assertions]

**Primary recommendation:** 保持 Tailwind v3 + 语义 CSS 变量架构不变，按“token/字体与桥接 → shared primitives → 壳层与高频页面 → feature 长尾与基线刷新”拆成 3-4 个可执行 plan，避免跨 plan 反复返工。 [VERIFIED: codebase read] [CITED: https://v3.tailwindcss.com/docs/theme]

## Architecture Patterns

### Recommended Project Structure

```text
src/
├── index.css                      # light/dark token source of truth
├── shared/view/ui/                # Button/Badge/Input primitive remap
├── components/ui/                 # bridge wrappers: button/select/dialog
├── components/home/view/          # landing shell calibration surfaces
├── components/app/view/           # tabs/shell chrome
├── components/auth/view/          # login/setup baseline screens
├── components/chat/view/          # high-traffic product surfaces
└── components/**                  # long-tail feature cleanup after primitive pass
public/
└── fonts/                         # Inter / GeistMono woff2 assets

tests/
└── visual/                        # deterministic visual fixtures and snapshots
```

该结构不是重组代码，而是规划上的实施层次：先改 token 和 shared primitives，再按“home/auth/app shell/chat core/long tail”顺序推进。 [VERIFIED: codebase read]

### Pattern 1: Token First, Utilities Second

**What:** 先在 `src/index.css` 写入 DESIGN.md 对应的语义变量，再在 `tailwind.config.js` 暴露 `fontFamily`、`letterSpacing`、`boxShadow`、`borderRadius`、`spacing` 等 utility。 [VERIFIED: codebase read] [CITED: https://v3.tailwindcss.com/docs/theme] [CITED: https://v3.tailwindcss.com/docs/customizing-colors]
**When to use:** 所有能通过 token 和 utility 消化的视觉规则都应先落这里，避免同一视觉决策在多个 feature 文件重复表达。 [VERIFIED: codebase read]
**Example:**

```typescript
// Source: https://v3.tailwindcss.com/docs/customizing-colors
extend: {
  colors: {
    background: 'hsl(var(--background))',
    foreground: 'hsl(var(--foreground))',
    brand: 'hsl(var(--brand))',
  },
  borderRadius: {
    pill: 'var(--radius-pill)',
    lg: 'var(--radius-large)',
  },
  boxShadow: {
    ring: 'var(--shadow-ring)',
    button: 'var(--shadow-button)',
  },
}
```

### Pattern 2: Stable Primitive APIs, New Visual Contracts

**What:** 保持 `variant` / `size` / props API 不变，只重写 `Button`、`Badge`、`Input`、`Select`、`Dialog` 的视觉契约。 [VERIFIED: codebase read]
**When to use:** 当某个样式变化会辐射全局，但调用方无需理解新设计系统时使用。 [VERIFIED: codebase read]
**Example:**

```typescript
// Source: current codebase primitive pattern in src/shared/view/ui/Button.tsx
const buttonVariants = cva(baseClasses, {
  variants: {
    variant: {
      default: 'rounded-pill shadow-button text-foreground hover:opacity-60',
      secondary: 'rounded-small border border-border shadow-subtle hover:opacity-60',
      ghost: 'rounded-pill text-muted-foreground hover:opacity-60 hover:text-foreground',
    },
  },
});
```

### Pattern 3: Fixture-Backed Visual Migration

**What:** 在刷新截图前，先提供可稳定复现的页面状态或 fixture route，确保截图不是依赖“当前刚好登录/刚好有 sidebar”。 [VERIFIED: codebase read] [CITED: https://playwright.dev/docs/test-snapshots]
**When to use:** 所有需要校验组件壳层、home、tabs、dialogs、chat composer 的视觉变更。 [VERIFIED: codebase read]
**Example:**

```typescript
// Source: https://playwright.dev/docs/test-snapshots
await expect(page).toHaveScreenshot('landing-dark.png', {
  maxDiffPixelRatio: 0.02,
  stylePath: './tests/visual/screenshot.css',
});
```

### Anti-Patterns to Avoid

- **并行 token 系统:** 不要在 CSS 变量之外再建一套 design token JSON/TS 常量层，否则 Phase 4 的语义 token 迁移价值会被抵消。 [VERIFIED: codebase read]
- **把 Tailwind v4 升级塞进本阶段:** v4 `@theme` 是另一条迁移线；当前阶段的最优路径是继续使用 v3 `theme.extend`。 [VERIFIED: codebase read] [VERIFIED: npm registry] [CITED: https://v3.tailwindcss.com/docs/theme] [CITED: https://tailwindcss.com/docs/theme#customizing-your-theme]
- **逐页面散改 hover / radius / shadow:** 先改 shared primitive 与 token，否则后续页面还要返工。 [VERIFIED: codebase read]
- **全局粗暴改 `opacity` 影响所有状态:** opacity-first hover 只应服务 hover 语言，不应削弱 focus-visible、disabled、destructive 语义。 [VERIFIED: codebase read] [ASSUMED]

## Migration Sequencing

### Recommended Plans

1. **Plan A: Token foundation + font pipeline + Tailwind bridge**  
   范围：`src/index.css`、`tailwind.config.js`、`public/fonts/`、`index.html`（如需要 preload）。先落色彩、spacing、radius、font stack、tracking、shadow token，并补 `brand` / `brand-foreground`。这样后续所有共享组件都基于同一套新基线开发。 [VERIFIED: codebase read] [CITED: https://vite.dev/guide/assets.html#the-public-directory] [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face]

2. **Plan B: Shared primitives + shell calibration surfaces**  
   范围：`Button`、`Badge`、`Input`、`Select`、`Dialog`，再加 `LandingPage` / `HomeFilters` / `FavoritesSection` / `RecentSessionsList` / `LoginForm` / `AppTabStrip`。这些文件能最大化验证新视觉语言是否成立，同时 API 变动最少。 [VERIFIED: codebase read]

3. **Plan C: High-traffic product surfaces**  
   范围：`ChatComposer`、核心 chat actions、sidebar/tab shell、常见 modal 壳层、settings/common panels。此阶段目标是把用户最常见的真实工作界面拉到同一视觉语言。 [VERIFIED: codebase read]

4. **Plan D: Long-tail cleanup + final baselines**  
   范围：剩余 feature 文件中的硬编码色阶、旧 hover 模式、灰/蓝/红直接类名、局部 modal 壳层与 tooltip/code styles，并刷新最终视觉回归基线。 [VERIFIED: terminal] [VERIFIED: codebase grep]

### Why This Order Minimizes Churn

- 先做 Plan A，后续任何圆角、阴影、tracking 都有统一 utility，不会在页面层重复写死。 [VERIFIED: codebase read]
- 先做 Plan B，Button/Select/Dialog 的视觉语言一旦定稿，Plan C/D 只需要“换用入口”而不是“重新发明样式”。 [VERIFIED: codebase read]
- 把长尾 cleanup 放最后，可以避免在设计规则尚未稳定时清 128 个文件，减少返工。 [VERIFIED: terminal]
- 视觉测试夹具应至少在 Plan B 前半段建立，否则截图只会记录“某次偶然状态”，无法稳定 gate 后续计划。 [VERIFIED: codebase read] [CITED: https://playwright.dev/docs/test-snapshots]

## Common Pitfalls

### Pitfall 1: 以为替换 token 就能完成迁移

**What goes wrong:** `src/index.css` 改完后，共享组件改善明显，但大量 feature 文件仍保留蓝/灰/红硬编码类与旧 hover 语义，最终页面风格仍然割裂。 [VERIFIED: codebase grep] [VERIFIED: terminal]
**Why it happens:** 当前至少 `128` 个文件含硬编码色阶，说明 token 并不是唯一视觉事实源。 [VERIFIED: terminal]
**How to avoid:** 把长尾 cleanup 单列成后续 plan，并优先清理高流量壳层与共享入口。 [VERIFIED: codebase read]
**Warning signs:** 截图里按钮/卡片已更新，但 modal、表单、消息条、文件树等局部区域仍明显偏蓝或偏白。 [VERIFIED: codebase grep] [ASSUMED]

### Pitfall 2: 把 Tailwind v4 资料直接套到当前仓库

**What goes wrong:** 规划中误用 `@theme`、theme variable namespaces 等 v4 语法，导致实施时必须顺手升级 Tailwind。 [VERIFIED: codebase read] [CITED: https://tailwindcss.com/docs/theme#customizing-your-theme]
**Why it happens:** npm latest 已是 `4.2.2`，官方首页文档默认也是 v4，而仓库仍在 `3.4.0`。 [VERIFIED: npm registry] [VERIFIED: codebase read]
**How to avoid:** 本阶段只采用 v3 文档中的 `theme.extend` / CSS variables bridge；把升级 Tailwind 视为独立未来阶段。 [CITED: https://v3.tailwindcss.com/docs/theme]
**Warning signs:** 计划里出现 `@theme`、`--color-*` theme namespace 改造、或要求全仓 CSS import 结构重写。 [CITED: https://tailwindcss.com/docs/theme#customizing-your-theme] [ASSUMED]

### Pitfall 3: 视觉回归基线不足且不稳定

**What goes wrong:** 改样式后快照要么覆盖不到关键页面，要么因登录态/动态内容不同而频繁 skip 或抖动。 [VERIFIED: codebase read]
**Why it happens:** 当前只有 2 张已落库快照，而且测试使用 `waitForTimeout()` 与基于当前 DOM 存在性的 `test.skip()`。 [VERIFIED: codebase read] [VERIFIED: terminal]
**How to avoid:** 先做 fixture route / stable state，再加 `landing`、`home cards`、`tabs`、`dialog`、`composer`、`settings shell` 等基线。 [VERIFIED: codebase read] [CITED: https://playwright.dev/docs/test-snapshots]
**Warning signs:** 更新快照时大量“截图通过但页面内容不一致”，或本地跑过、CI 跑不过。 [CITED: https://playwright.dev/docs/test-snapshots] [ASSUMED]

### Pitfall 4: 字体接入只换 `font-family` 不处理权重与加载

**What goes wrong:** 页面看上去“像换了字体”，但字重、行高、FOUT、截图差异都不稳定。 [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face] [CITED: https://v3.tailwindcss.com/docs/font-family]
**Why it happens:** 当前 `body` 还是系统字体栈，仓库里也没有 `public/fonts/`。 [VERIFIED: codebase read]
**How to avoid:** 先确认字体文件来源，再用 `@font-face` 明确 `font-family`、`font-weight`、`font-style`、`font-display`，并同步 Tailwind `fontFamily`。 [VERIFIED: codebase read] [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face] [CITED: https://v3.tailwindcss.com/docs/font-family]
**Warning signs:** 文本重排、按钮高度轻微变化、Playwright 快照在不同机器上持续抖动。 [CITED: https://playwright.dev/docs/test-snapshots] [ASSUMED]

### Pitfall 5: 把 opacity-first hover 用成“全局降可读性”

**What goes wrong:** hover 统一后，ghost、secondary 看起来更一致，但 destructive、focus、disabled 的层级也被误伤。 [VERIFIED: codebase read] [ASSUMED]
**Why it happens:** 当前仓库很多控件把 hover、active、focus、disabled 混在同一串 utility 里。 [VERIFIED: codebase grep]
**How to avoid:** 只改 hover contract，保留独立的 `focus-visible` / `disabled` / destructive ring 逻辑。 [VERIFIED: codebase read]
**Warning signs:** destructive 按钮 hover 后与普通 CTA 区分度下降，或 focus ring 不再足够显眼。 [VERIFIED: codebase read] [ASSUMED]
